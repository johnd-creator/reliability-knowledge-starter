# Engineering Workspace threat model — candidate, source-free
Scope: the Phase 2 candidate introduced after baseline e67c641e23214bf8851a05d312e1426c1e471ec3. This is a requested design assessment, not a complete repository vulnerability scan or operational penetration test.

## Overview
Human case records are separate from collector facts. The protected assets are investigator notes, accountable review decisions, canonical evidence lineage, revision history and private configuration. Potential adversaries include unauthenticated visitors, an authenticated author exceeding asset scope, a contributor fabricating independent review, malicious note content and a privileged database operator.

Production `create_app` is unchanged and does not mount Engineering routes. An environment flag cannot enable operational writes. The candidate router and service can run only with explicitly injected dependencies in isolated acceptance tests. The UI is a synthetic in-memory development prototype; its actor selector is a simulation, never authentication. No production identity provider, application migration runner or operational writer bootstrap is supplied.

## Trust boundaries and assumptions
1. Browser → future application identity adapter: untrusted text and record IDs; identity must come from a reviewed server-side provider, never request headers or form fields. Session revocation, request origin/CSRF protection and product RBAC remain activation prerequisites.
2. Principal → case service: roles, exact asset scopes, ownership/current assignment and independent reviewer checks are enforced. A caller injecting a forged Principal is outside the trusted adapter boundary and must never be reachable from public input.
3. Case service → application repository: explicit engine injection only; no secret/environment fallback. Case, event and idempotency receipt share one transaction. Expected revision is compared atomically in SQL.
4. Evidence provider → existing Mart: local SELECT-only adapter, exact registry identity and bounded local record lookup. Governed condition evidence requires VERIFIED mapping and approved signal. No source client, arbitrary URL or remote discovery.
5. Application writer → audit tables: isolated PostgreSQL tests prove a limited writer cannot update/delete/truncate audit or alter tables. Deployment grants and an independently protected retention/export mechanism are still required; a database owner can tamper.
6. Repository publication: fixtures are synthetic and reports contain repository-relative source references. No private runtime inventory or credentials are needed.

Dependencies and accepted inherited models remain part of the trusted computing base. Authentication correctness cannot be inferred from disabled contracts. Feature flags are availability controls, not authorization.

## Severity calibration and review disposition
Unauthorized writes or forged approvals would have HIGH integrity impact if an operational writer were exposed without trusted identity. Cross-asset note disclosure would have HIGH confidentiality impact where records contain restricted operational information. These are activation risks, not demonstrated public vulnerabilities in this disabled candidate. Availability concerns are bounded locally but operational rate/retention controls remain outstanding.

Gate A PASS is limited to disabled contracts, isolated fixtures and the explicit development prototype. Operational write/review activation remains BLOCKED. There is no claim of secure production authentication or tamper-proof owner administration.

An independent read-only architecture review examined the baseline and candidate. It confirmed the separation of application/Mart storage, absent production router mounting, explicit principal/asset gates, contributor review exclusion, local evidence resolution and atomic SQL concurrency. The review was task-scoped, not an exhaustive scan or runtime assessment. Graph generation preceded the candidate; exact source and tests were used for new paths.

Validation covers no-auth denial, role/ownership/asset scope, actor spoofing, independent reviews, invalid transitions, untrusted notes, bounded evidence, transaction rollback, stale and simultaneous revisions, receipt replay and audit privilege denial. Public release documentation records exact suite counts and skipped infrastructure tests.
